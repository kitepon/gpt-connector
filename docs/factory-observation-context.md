# Optional GPT factory observation context

Source-only implementation of Fr's adopted seven-scalar contract in `docs/gpt-observation-context-20261026.md`. The product owns primitive retention and scalar mapping, Dorothy owns preservation/projection within the same factory report, and Fr owns central allowlist/value shapes/privacy/display. No host execution, new probe or send is enabled here.

The normal factory diagnostic uses its existing single session fetch and evaluation. Its user result becomes a boolean immediately; only HTTP status and already evaluated bridge comparison booleans are retained. Original bridge short circuit is preserved: after a version mismatch the build and summary fields are uninspected; after a build mismatch summary is uninspected. No bridge is initialized and no actual user/build identifiers, body, header, URL or exception text enters the group.

`encodeGptObservationContext` emits the exact seven fixed strings. Missing/nonprimitive observations become unobserved/uninspected. Non-2xx HTTP never supplies user status. Absent/uninspected bridge never supplies version/build/summary status. `readGptObservationContext` accepts group absence or an empty object for old reports, validates the whole seven-key group, rejects partial/extra/invalid/contradictory groups, and emits one fixed error without values. Returned groups are owned frozen snapshots.

The native source option `factoryDiagnostics({ includeObservationContext: true })` attaches the same group to the auth and runtime_bridge checks from that single observation. Existing check ID/status/reason/overall are unchanged. This option defaults to false, has no CLI flag, and is not enabled by `factory-diagnostics --json`; the current report path receives no nonempty group. Missing legacy primitive results are not reconstructed, and unsupported/error paths keep their existing omitted group. No runtime-error record or fingerprint is changed.

After central and factory source acceptance and normal integration, owners must explicitly agree how the native diagnostic opt-in is supplied by the existing single factory invocation. The product does not add a second diagnostic call or silently enable it from an environment variable. Ordinary release/deployment/send require the remaining existing gates; this source candidate is not that authorization.

New isolated tests exercise the generated expression with fake in-memory fetch/global values and the scalar projector/validator. They perform no HTTP/CDP/browser/host operation and do not rerun the old classifier five cases or public release/install suites.
