# Windows同一SIDの対話Chrome起動修理

現在のSSH/Session0経路でWMI Win32_Process.Createを直接呼ぶと、ChromeもSession0へ作成され、利用者のExplorer/Session1から操作できなかった。今回06:23の現在観測であり、旧10/11のf050内部原因をこの観測だけで確定しない。

Windows adapterのspawnDetachedが、既存window操作用TaskScheduler入口と同じ所有責務を使うよう整理した。windows-interactive.tsが同一SIDの既ログインExplorer/sessionを選び、固有名・同一SID/LUA/InteractiveToken・TASK_CREATE（既task上書き無し）・RunEx USE_SESSION_IDの有限taskを持つ。複数sessionなら現在のinteractive sessionを優先し、Session0から一意に選べない時は失敗する。他利用者/全利用者service/S4U/パスワード/昇格へのfallbackは無い。

taskのworkerは実SID/session>0/期限を再照合してから操作し、nonce/SID/session/安全な成否receiptを私有directoryへatomic moveする。controllerがtask所有者/説明を確認し、成功・worker失敗・期限切れとも自分のtaskだけ停止/削除する。回収確認の失敗は安全errorとして可視化し、私有receiptを残して完了を装わない。window操作も同helperへ統一し、対象process同一SID/sessionを検査してからWin32 APIを呼ぶ。起動workerは既存WMI作成を対話session内で行い、子processの同SID/sessionを検査する。WMI経由の独立寿命と引数引用を維持する。

保存結果はbot artifacts/2026-10-25-windows-interactive-launch/。有限無害probeはInteractiveToken同SID/Session1、WMI Node子がtask削除後も生存し所有tagだけ回収、worker例外/期限切れが失敗として返りtask回収されることを確認。候補compiled moduleを通常npm配備の所有一時directoryへstageし、新test/windows-interactive.test.tsの実Windows検査をpass1/fail0/skip0で確認した（成功/失敗/期限の3枝）。製品公開版は書き換えない。
